# AI 开发协作

本目录用于共同研究、记录和改进 AI 辅助开发的方式。它与产品方法论 Wiki 用途不同：这里讨论如何开发 PIck，Wiki 讨论用户找导师时采用的方法。

核心入口是 [AGENTS.md](../AGENTS.md)；项目状态与产品边界见[产品底稿](../docs/product-foundation.md)。

## 已确认的长期协作规则

### 分工与决策

- 用户决定产品方向、功能优先级、体验取舍和最终验收。AI 承担技术调研、实现方案、代码、测试、部署说明及必要工程维护。
- AI 应主动指出问题并给出有依据的建议，不替用户确定未经确认的产品需求，也不把技术选型变成未经分析的问卷。
- 普通实现细节在已确认边界内自主处理。对明显影响成本、数据隐私、产品体验、长期维护或难以撤销的决定，用易懂的方式解释影响、给出推荐，再由用户确认。

### 按真实需求推进

- 接到任务后先检查已有材料，说明理解，区分已确认内容、建议、假设和开放问题。
- 每轮只提出少量真正影响近期决策的问题，不要求提前提供完整功能清单。
- 讨论形成共识后，确定足够小的实现范围和验收标准，确认后实施。只为当前需求引入必要结构，同时让增加、修改、替换和删除功能保持可控。
- 使用 AI 开发不构成加入产品 AI 功能的理由。

### 复用与调研

- 优先复用成熟、维护良好、许可适配的框架、组件、库和模板；不要求套用完整平台，也不机械拼接多个仓库。
- 推荐重要依赖或模板前，实际查阅官方资料和仓库，说明适配程度、维护情况、许可、部署要求及引入的复杂度；未核实内容明确标注。
- 对项目独有业务或复用成本明显超过收益的部分，可以编写必要代码，并说明理由。

### 实施交付

每次交付简短报告：

1. 改了什么，以及对应的已确认需求。
2. 实际执行了哪些检查或测试及其结果。
3. 有哪些未验证事项或已知限制。
4. 用户如何验收。

未执行的工作不能写成已完成，不编造启动、测试或部署命令，不以“代码写完”代替可靠性验证。

## 研究、提案与规则如何区分

- **研究资料**：记录实际查阅的来源、查阅时间、观察和适用边界；外部实践不是自动生效的项目规则。
- **待讨论提案**：明确建议内容、理由、影响和待确认事项；未经确认不得表述为已经采用。
- **已确认生效的规则**：只记录用户明确提出或确认的约定；核心规则放在根目录入口，详细协作约定放在本目录。

目前本文件的“已确认的长期协作规则”即生效约定。以后有具体研究或提案时，再增加必要文件并在这里链接，标明类别和状态；不预建空目录、空模板或庞大制度。提案经用户确认后再更新相应规则，避免保留相互冲突的版本。
